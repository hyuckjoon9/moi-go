# 모이고 QA 진행 정리

작성일: 2026-07-23

프론트 프로토타입 QA부터 백엔드 검증, 정책 결정, 백오피스 검증까지 지금까지 진행한 전체 과정을, "어떤 상황(시나리오)에서 문제를 발견했고 → 어떻게 해결했는지" 기준으로 정리한다.

---

## 1. 프론트엔드 QA

프론트 프로토타입을 직접 조작해보면서 발견한 문제들. 모두 수정 완료.

| 발견한 상황(시나리오) | 문제 | 조치 |
|---|---|---|
| 그룹 홈에서 "모집글 작성" 클릭 | 모집글 탭으로 이동만 되고, 사용자가 한 번 더 클릭해야 작성 다이얼로그가 열림 | 클릭 즉시 작성 다이얼로그가 열리도록 수정 |
| 모집글 상세 화면에서 계정을 전환 | 작성자 전용 버튼(수정/삭제/모집종료/활동종료/신청자관리)이 이전 계정 기준으로 그대로 남고, 참가 신청 버튼이 안 보임 | 계정 전환 시 현재 로그인 계정 기준으로 버튼 상태를 다시 계산하도록 수정 |
| 모집 종료 클릭 | "일정을 조회했습니다"라는 엉뚱한 성공 메시지가 뜸 | 액션별 성공 메시지를 분리 |
| 신청 승인 클릭 | "일정을 조회했습니다"가 뜸 | 액션별 성공 메시지를 분리 |
| 모집글 수정 후 | "모집글 상세를 조회했습니다"가 뜸 | 액션별 성공 메시지를 분리 |
| 모집 종료 후 화면 | 상태가 "모집 중"으로 그대로 남아 있음(즉시 갱신 안 됨) | 종료 후 화면 상태 즉시 갱신 |

이 외에 목록·아래 항목들도 같은 시기에 함께 처리됨(작성자 본인 참가신청 버튼 숨김/작성자용 버튼 노출, 모집글 작성 성공 후 목록 자동 재조회, 그룹 홈 활성 그룹원을 요약 카드 토글로 표시(닉네임/프로필 이미지 중심, 내부 ID 미노출), 일정 관리를 제목/날짜 기준으로 선택(ID 직접 조작 없이), 일정 최신순 정렬 및 생성 후 자동 재조회, 참석·출석 응답 JSON 원문 노출 금지(성공/실패 메시지와 갱신된 현황만 표시), 일반 MEMBER 화면에서 관리 기능 숨기고 본인 정보만 노출).

## 2. 백엔드 QA — 파트별

### Part1 (회원·인증) 
- 프로필 이미지 업로드/URL 저장 기능 완료 확인.
- 로그아웃 시 DB 재생성 등으로 회원/토큰 정보가 꼬인 경우에도 프론트가 로컬 토큰을 정리하도록 응답 정책 확인 및 반영 완료.
- `WITHDRAWN`(탈퇴) 회원의 로그인/토큰 재발급/내 정보 조회 제한이 일관되게 동작하는 것까지 확인 완료.
- 이상 항목 **전부 해결 확인.**

### Part2 (모집·참가 신청) 
발견한 상황들과 처리 결과. **전부 완료.**

| 발견한 상황 | 조치 |
|---|---|
| 마감일이 지난 모집글도 계속 등록/수정 가능했음 | `@FutureOrPresent` 검증 추가 — 오늘 이후 날짜만 허용 |
| "모집글 삭제 vs 종료만 허용" 정책 미정 | **종료만 허용**으로 확정, 삭제 API 없음 유지 |
| 모집글 상세 응답에 현재 사용자 기준 권한 필드가 없어 프론트가 버튼 노출 여부를 스스로 판단해야 했음(계정 전환 버그의 근본 원인) | `leaderId`, `isOwner`, `isJoined`, `canApply`, `canManage` 필드 추가 |
| 모집글 상세 응답에 일부 필드 누락 | `description`/`goal`/`method`/`meetingType`/`location`/`onlineLink`/`meetingDay`/`capacity`/`recruitmentDeadline`/`expectedDuration`/`conditions`/`leaderId` 모두 포함하도록 정리 |
| 모집 종료/수정/승인 후 최신 상태를 바로 확인하기 어려움 | 응답/조회 API 정리 |
| 이미 가입한 그룹의 모집글에 재신청 시 에러 메시지가 불명확 | "이미 참여 중인 그룹입니다"로 명확화 |
| 신청 승인 시 그룹원 추가가 정상 처리됐는지 확인 어려움 | 응답/후속 조회로 확인 가능하도록 정리 |
| **(오늘 추가로 검증)** 마감(CLOSED)된 모집글을 다시 열 방법이 없어서, 인원 충원이 필요할 때 사실상 "삭제 후 재작성"을 유도하는 문제 | **재모집(reopen) 기능** 신설 — `PATCH /{id}/reopen`, CLOSED 상태에서만 허용, 내용 수정 + `RECRUITING` 전환을 하나의 트랜잭션으로 처리. 서비스/컨트롤러/테스트까지 구현 및 팀 저장소 반영 확인 완료 |

### Part3 (그룹·일정) 
- 내 그룹 목록 조회 API 구현 및 머지 완료 확인.
- 그룹 홈 활성 그룹원 응답에 `nickname`/`profileImageUrl` 포함되도록 수정 완료 확인(프론트의 "내부 ID 노출 금지" 요구사항과 연결).
- "그룹 삭제 vs 종료만 허용" 정책 확정(Part2와 동일하게 **종료만 허용**).
- 그룹 홈에서 모집글 작성/관리 흐름, 그룹-모집글 연결 정책 확정.
- "일정 생성 후 일정 조회가 안 되는" 문제 — 생성 API 응답, 전체/다가오는 일정 조회 조건, 날짜 필터 기준을 재확인해서 해결.
- 일정 목록 응답에 ID/제목/일시/장소·링크/내용을 충분히 포함해서 프론트가 ID를 직접 다루지 않아도 되게 정리.
- 일반 MEMBER도 그룹 홈에서 본인 일정/참석 응답/출석 상태를 조회할 수 있도록 처리.
- 이상 항목 **전부 해결 확인.**

### Part4 (출석·활동) 
- 참석 응답 수정, 출석 체크 수정 기능 구현.
- 참석 응답/출석 체크 저장·수정을 하나의 API(또는 버튼)로 처리하는 정책 확정 및 반영.
- 참석 현황 조회 API(일정별 참석/불참/미정 응답 수, 사용자별 응답 상태) 구현.
- 개인 출석률 조회 API 구현 — 일반 MEMBER 본인 확인 가능.
- 그룹장/매니저의 그룹원별 출석 현황 조회 기능 구현.
- 활동 기록(`activity_records`)·회고 리뷰 기능 구현.
- 활동 회고(리뷰) 관련해서는 QA 과정에서 "다른 계정 작성 불가", "저장 시 엉뚱한 삭제 관련 메시지 노출", "그룹 전환 시 이전 그룹 데이터 잔존", "권한 메시지 오탐" 등이 추가로 발견됐으나(6번 참고), 이후 원인 진단·수정을 거쳐 **모두 해결 확인.**
- 이상 항목 **전부 해결 확인.**

## 3. 정책 결정 사항

QA 과정에서 애매했던 부분을 팀이 논의해서 확정한 정책들.

| 쟁점 | 결정 |
|---|---|
| 그룹/모집글을 실제 삭제 허용할지 | **종료 상태로만 관리, 실제 삭제 없음** — 출석/활동 이력 보존 목적 |
| 백오피스에서만 처리할 관리 기능 vs 일반 화면에서 가능한 운영 기능 구분 | 백오피스 기능 구현 완료로 정리됨(4번 참고) |
| 모집글 작성 흐름(그룹 먼저 vs 모집글 작성 시 자동 그룹 생성), 모집 종료-그룹 활동 종료 관계, 참석 응답 마감 전 수정 허용 여부, 출석 체크 권한(그룹장만 vs 매니저 포함), 일반 MEMBER 그룹 홈 노출 범위 | 우선순위 작업을 거치며 순차적으로 확정·반영 (아래 5번 우선순위 항목과 연동) |

## 4. 백오피스(Back Office) 구현 및 검증

백엔드·프론트엔드 구현 완료, PR 반영. 병합 충돌 없음, 각 파트 추가 작업 없음.

**진입 방법**: `http://localhost:8080/backoffice/index.html`, `ADMIN` 권한 계정 로그인 필요 (개발 계정 `admin@moigo.test` / `Admin1234!`)

**DB 반영**: `sql/moigo_schema_seed.sql`을 로컬 개발 DB 초기화 시 사용(테이블 삭제 후 재생성 — 보존할 로컬 데이터 있으면 실행 주의).

**구현된 기능**
- 대시보드 — 회원·모집글·그룹 현황 및 최근 운영 조치 조회
- 회원 관리 — 검색·필터·상세 조회, 일반 회원 이용 정지/해제, 상태 변경 사유·운영 이력 확인
- 모집글 관리 — 검색·필터·상세 조회, 숨김/복구, 숨김·복구 이력 확인
- 그룹 운영 조회 — 그룹/일정/출석/활동 기록 조회 (현재는 읽기 전용, 상태 변경·삭제 없음)
- 운영 이력 — 회원 정지·해제, 모집글 숨김·복구 이력 검색·조회

**검증한 시나리오**

1. **관리자가 회원을 정지시킨 상황** → 대상 회원의 이후 API 요청이 인증되지 않음, 재로그인·토큰 재발급도 실패하는 것을 확인.
2. **관리자가 공개 모집글을 숨긴 상황** → 일반 사용자 목록에서 사라짐, 기존 상세 URL 접근도 실패, 복구 후 다시 정상 조회되는 것까지 확인.
3. **그룹 운영 조회에서 그룹·일정·출석·활동을 검색한 상황** → 검색 조건에 따라 결과만 바뀌고, 상태 변경/삭제 버튼은 노출되지 않는 것(읽기 전용 원칙 유지) 확인.

3. 일정 생성 후 일정 조회 문제 — 완료
4. 모집글 수정/종료/승인 후 상태·메시지 갱신 문제 — 완료
5. 참석 응답 수정 및 출석 체크 수정 기능 — 완료

## 6. 활동 회고(리뷰) 관련 이슈 — 발견 및 해결

우선순위 처리가 끝난 뒤, 실제 시나리오로 다시 QA하는 과정에서 추가로 발견해 해결한 문제들. **모두 해결 완료.**

| 발견한 상황(구체적 재현 사례 포함) | 증상 |
|---|---|
| 리더가 아닌 다른 계정으로 활동 회고를 작성 시도 | 회고 작성이 안 됨 |
| 회고를 저장 | "연관된 그룹 또는 지원 내역이 있어 삭제할 수 없습니다"라는, 삭제와 무관한 메시지가 뜸. 운영 중인 다른 그룹에서도 동일하게 회고 작성 자체가 안 됨 |
| A 그룹 홈에서 B 그룹 홈으로 전환 | 출석/회고 화면이 갱신되지 않고 이전 그룹 데이터가 그대로 보임 — 구체적으로 "그룹 ㅇㅇㅇ의 출석·회고(111)"가 "그룹 ㅁㅁㅁ" 화면에서도 그대로 노출되는 크로스 그룹 데이터 잔존 확인 |
| 내가 운영자인 새 계정에서 회고 작성 시도 | 회고 작성 화면이 바로 안 뜨고, 회고 조회를 한 번 거쳐야 보임 |
| 회고 작성 시도 시(재현할 때마다 메시지가 다름) | "활동 기록을 관리할 권한이 없습니다"가 뜨는 경우도 있음 — 회고 작성 자체가 막히는 건 공통 |

**원인 진단 및 조치**
- "삭제할 수 없습니다" 메시지는 `GlobalExceptionHandler`가 모든 `DataIntegrityViolationException`을 무조건 이 메시지로 고정 응답하던 전역 버그였음. 회고 저장 시 중복 리뷰(유니크 제약) 또는 `comment` 미검증(`@NotBlank` 없음)으로 인한 DB NOT NULL 위반이 이 마스킹된 메시지로 나온 것으로 확인, 검증 로직 보강 및 예외 처리 개선으로 해결.
- "활동 기록을 관리할 권한이 없습니다"는 원래 "활동 기록(record, 리더/매니저 전용)" API의 에러 메시지였는데, 프론트가 "활동 회고(review, 그룹원 누구나 가능)" 작성 시 다른 API를 잘못 호출하고 있던 것이 원인 — 프론트 호출 경로 수정으로 해결.
- 그룹 전환 시 데이터가 안 바뀌던 문제는 프론트가 그룹 전환마다 재조회를 하지 않던 상태 관리 문제로 확인, 재조회 로직 추가로 해결.

## 7. 결과

QA 과정에서 발견된 프론트/백엔드(Part1~4)/정책/백오피스 관련 이슈 전 항목 해결 완료.
