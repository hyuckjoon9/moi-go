# Part2 모집글·지원 기능 명세

> 이 문서는 기획·프론트엔드·백엔드가 공유하는 사용자 기능과 업무 규칙의 기준이다. HTTP 필드와 예시는 [api.md](api.md)를 참고한다.

## 목적과 범위

Part2는 스터디 모집글의 작성부터 지원자 관리, 모집 종료까지의 흐름을 제공한다. 모집글이 만들어지는 즉시 Part3 스터디 그룹이 함께 생성되고, 지원이 승인될 때마다 해당 그룹에 멤버가 실시간으로 추가된다.

| 범위 | 포함 기능 | 제외 기능 |
| --- | --- | --- |
| 모집글 | 작성, 목록·상세 조회, 수정, 삭제, 마감, 종료 | 그룹 홈, 일정 관리(Part3 영역) |
| 지원 | 등록, 지원자 목록 조회, 승인, 거절, 내 신청 목록 조회 | 그룹원 역할 변경, 그룹 탈퇴(Part3 영역) |

## 용어와 상태

| 용어 | 값 | 의미 |
| --- | --- | --- |
| 모집글 상태 | `RECRUITING`, `CLOSED`, `ACTIVE`, `ENDED` | 모집 중 → 마감 → (활성 스터디) → 종료 |
| 지원 상태 | `PENDING`, `APPROVED`, `REJECTED`, `CANCELLED` | 대기 → 승인 또는 거절. `CANCELLED`(지원 취소)는 Entity 메서드만 있고 아직 어떤 Service·API에서도 호출되지 않음(미완성 기능) |

## 사용자별 권한

| 사용자 | 모집글 조회 | 모집글 수정·삭제·마감·종료 | 지원 등록 | 지원자 목록·승인·거절 |
| --- | --- | --- | --- | --- |
| 리더(작성자) | 가능 | 가능 | 불가(자기 모집글에는 지원 불가) | 가능 |
| 리더가 아닌 로그인 사용자 | 가능 | 불가 | 가능(`RECRUITING` 상태에서만) | 불가 |
| 비로그인 | 불가 (`SecurityConfig`상 모든 `/api/recruitment-posts/**`가 인증 필수, 목록·상세도 예외 아님 — 확인 완료) | 불가 | 불가 | 불가 |

## 기획·프론트엔드 기능 흐름

### 모집글 작성

1. 사용자가 모집글을 작성하면 즉시 저장되고 상태는 `RECRUITING`이다.
2. 저장과 동시에 스터디 그룹이 자동으로 만들어지고 작성자는 해당 그룹의 리더로 등록된다. 별도의 "그룹 확정" 단계는 없다.
3. 화면에서는 모집글 작성 완료 시점에 "내 그룹"에도 해당 스터디가 리더 역할로 즉시 노출될 수 있음을 안내한다.

### 모집글 목록·상세

1. 목록은 카테고리 필터와 페이지네이션을 지원한다.
2. 상세에서는 모집 정보 전체(목표, 방법, 모집 인원, 마감일 등)와 현재 상태를 보여준다.

### 모집글 수정

1. 리더만 수정할 수 있다.
2. 수정은 부분 수정이 아닌 전체 교체이며, 화면은 기존 값을 채워 다시 전송한다.

### 모집 마감

1. 리더가 마감을 선택하면 상태가 `CLOSED`로 바뀌고, 이후 신규 지원은 받을 수 없다.
2. 이미 승인된 지원자·그룹원 구성에는 영향이 없다.

### 스터디 종료

1. 리더가 스터디를 종료하면 모집글 상태가 `ENDED`로 바뀌고, 연결된 스터디 그룹도 함께 종료된다.
2. 종료 이후에는 해당 그룹의 일정 관리(Part3)도 불가능해진다.

### 모집글 삭제

1. 리더만 삭제할 수 있다.
2. 현재 설계상 모집글 작성 즉시 그룹이 생성되므로, 그룹이 연결된 모집글은 삭제할 수 없다. 화면에서는 "삭제 대신 마감/종료를 이용하라"는 안내가 필요할 수 있다(정책 확정 필요 — 아래 "완료 조건" 참고).

### 지원 등록

1. `RECRUITING` 상태의 모집글에만 지원할 수 있다.
2. 리더 본인은 자신의 모집글에 지원할 수 없다.
3. 같은 모집글에 중복 지원할 수 없다.

### 지원자 목록 조회·승인·거절

1. 리더만 지원자 목록을 볼 수 있고, 승인·거절도 리더만 할 수 있다.
2. 승인하면 지원 상태가 `APPROVED`로 바뀌고, 동시에 해당 지원자가 스터디 그룹에 멤버로 자동 추가된다. 실패(예: 그룹이 이미 종료됨)하면 승인 자체가 롤백된다.
3. 거절하면 지원 상태가 `REJECTED`로 바뀌며 그룹에는 아무 변화가 없다.
4. 이미 승인/거절된 지원서는 다시 처리할 수 없다.

### 내 신청 목록 조회

1. 지원자는 자신이 지원한 모든 모집글의 상태를 확인할 수 있다.
2. 상태별 필터(`PENDING`/`APPROVED`/`REJECTED`)를 지원한다.

## 백엔드 구현 기준

### 접근 검증 순서

모집글 관리(수정·삭제·마감·종료) 요청은 아래 순서로 검증한다.

1. 모집글 존재 여부
2. 요청자가 리더 본인인지 여부

지원 처리(승인·거절) 요청은 아래 순서로 검증한다.

1. 모집글 존재 여부
2. 요청자가 리더 본인인지 여부
3. 지원서가 해당 모집글 소속인지 여부
4. 지원서 상태가 `PENDING`인지 여부

지원 등록 요청은 아래 순서로 검증한다.

1. 모집글 존재 여부
2. 요청자가 리더 본인이 아닌지 여부(본인이면 거부)
3. 모집글 상태가 `RECRUITING`인지 여부
4. 중복 지원 여부

### 데이터와 연동 경계

- 그룹 프로비저닝은 Part2가 Part3의 `StudyGroupProvisioningPort`를 호출해 요청한다. 모집글 작성 시 `createGroup`, 지원 승인 시 `addMember`, 스터디 종료 시 `endGroup`을 사용한다. 과거의 일괄 `confirmGroup()` 방식은 폐기됐다(자세한 내용은 [`study-group-integration-design.md`](study-group-integration-design.md) 참고).
- Part2는 Part3의 `StudyGroup`/`GroupMember` Entity나 Repository를 직접 참조하지 않고 공개 포트(`StudyGroupProvisioningPort`)와 식별자(`postId`, `userId`)만 사용한다.
- `postId`는 그룹 생성의 멱등 키이므로, 같은 모집글에 대해 `createGroup`이 중복 호출돼도 그룹은 하나만 유지된다.

## 화면 처리 기준

| 상황 | 권장 처리 |
| --- | --- |
| `UNAUTHORIZED` | 로그인 화면 또는 재인증 흐름으로 이동 |
| `RECRUITMENT_ACCESS_DENIED`, `APPLICATION_ACCESS_DENIED` | 권한 없음 안내, 관리 UI를 노출하지 않음 |
| `RECRUITMENT_NOT_FOUND`, `APPLICATION_NOT_FOUND` | 목록으로 이동, 새로고침 안내 |
| `RECRUITMENT_CLOSED` | 지원 버튼 비활성화, 마감 안내 |
| `SELF_APPLICATION_NOT_ALLOWED` | 지원 버튼 자체를 리더 본인 화면에서 숨김 |
| `DUPLICATE_APPLICATION` | 이미 지원했음을 안내하고 내 신청 목록으로 유도 |
| `APPLICATION_ALREADY_PROCESSED` | 새로고침 후 최신 상태 표시 |
| `RECRUITMENT_DELETE_NOT_ALLOWED` | 삭제 불가 사유 안내, 마감/종료 유도 |

## 완료 조건

- 리더는 모집글 작성 즉시 자신의 스터디 그룹을 확인할 수 있다.
- 지원 승인 시 별도 조작 없이 지원자가 그룹 멤버로 반영된다.
- 모집글 상태(RECRUITING/CLOSED/ACTIVE/ENDED)와 그룹 상태(ACTIVE/ENDED)가 종료 시점에 일치한다.
- API 요청·응답 필드는 `api.md`와 실제 DTO가 일치한다.
- (미결) 그룹이 연결된 모집글의 삭제 정책이 확정되고 문서·구현·화면이 일치한다.
