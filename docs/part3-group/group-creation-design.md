# 그룹 생성 유스케이스 설계

> 작성일: 2026-07-20

## 목적

Part2가 전달한 모집 결과로 스터디 그룹과 초기 그룹원을 한 번만 생성한다. 같은 모집
결과가 재전달되거나 동시에 전달되어도 중복 데이터를 만들지 않고 기존 그룹 식별자를
반환한다.

## 범위

이번 작업은 Part3의 서비스 유스케이스와 해당 테스트를 구현한다.

- Part2가 Part3의 공개 서비스를 직접 호출한다.
- 그룹 생성 입력 계약과 결과 계약을 Part3가 제공한다.
- 그룹과 초기 그룹원 저장을 하나의 트랜잭션으로 처리한다.
- 순차·동시 재요청을 멱등하게 처리한다.
- 외부 모집글과 사용자 존재 여부는 호출자인 Part2가 보장한다.
- Part1·Part2 Entity 또는 Repository를 직접 참조하거나 수정하지 않는다.
- HTTP Controller와 외부 공개 API는 이번 범위에 포함하지 않는다.

## 공개 계약

Part2는 다음 값을 `CreateStudyGroupCommand`로 전달한다.

| 필드 | 타입 | 규칙 |
| --- | --- | --- |
| `postId` | `Long` | 필수, 그룹 생성의 멱등 키 |
| `groupName` | `String` | 필수, 공백 제거 후 빈 값 불가 |
| `leaderUserId` | `Long` | 필수, 최초 `LEADER` |
| `approvedUserIds` | `List<Long>` | 필수 목록, 빈 목록 허용, null 원소 불가 |

`StudyGroupCreationService.create(command)`는 생성되었거나 이미 존재하는 그룹의 `Long`
식별자를 반환한다. 같은 `postId`로 이름이나 회원 목록이 다른 재요청이 들어와도 최초 생성
결과를 유지하며 기존 그룹 식별자를 반환한다. 기존 데이터를 재동기화하는 기능은 별도
유스케이스로 다룬다.

## 컴포넌트와 책임

### `CreateStudyGroupCommand`

- Part2와 Part3 사이의 입력 경계를 표현한다.
- 필수값, 그룹명과 승인 회원 목록의 기본 형식을 생성 시점에 검증한다.
- 승인 회원 목록을 방어적으로 복사한다.

### `StudyGroupCreationService`

- Part2가 호출하는 공개 유스케이스 진입점이다.
- 먼저 `postId`로 기존 그룹을 조회하고 존재하면 그 식별자를 반환한다.
- 신규 생성은 트랜잭션 전용 컴포넌트에 위임한다.
- 동시 생성 중 유니크 제약 충돌이 발생하면 트랜잭션 종료 후 기존 그룹을 다시 조회한다.
- 기존 그룹이 확인되지 않으면 원래 저장 예외를 다시 던져 FK 오류 등을 숨기지 않는다.

### `StudyGroupCreationWriter`

- 별도 Spring Bean으로 두어 프록시 기반 트랜잭션 경계를 보장한다.
- 그룹과 모든 초기 그룹원을 단일 트랜잭션에서 저장한다.
- 모집장을 먼저 `LEADER`로 추가한다.
- 승인 회원 ID의 순서를 유지하면서 중복을 제거하고, 모집장 ID는 제외한 뒤 `MEMBER`로
  추가한다.
- 저장 과정이 실패하면 그룹과 그룹원 변경을 모두 롤백한다.

## 처리 흐름

1. `CreateStudyGroupCommand`가 입력을 검증하고 승인 회원 목록을 복사한다.
2. `StudyGroupCreationService`가 `postId`로 기존 그룹을 조회한다.
3. 기존 그룹이 있으면 기존 그룹 ID를 즉시 반환한다.
4. 기존 그룹이 없으면 `StudyGroupCreationWriter`가 새 트랜잭션에서 그룹을 저장한다.
5. Writer가 모집장을 `LEADER`로 저장한다.
6. Writer가 중복과 모집장을 제거한 승인 회원을 `MEMBER`로 저장한다.
7. 트랜잭션 커밋 후 생성된 그룹 ID를 반환한다.
8. `post_id` 유니크 제약 충돌이면 Service가 기존 그룹을 다시 조회해 그 ID를 반환한다.

## 멱등성과 동시성

애플리케이션의 선조회는 일반적인 재요청을 빠르게 처리한다. 동시에 들어온 두 요청이 모두
선조회를 통과할 수 있으므로 데이터베이스의 `study_groups.post_id` 유니크 제약을 최종
동시성 경계로 사용한다.

유니크 제약 위반은 Writer 트랜잭션 밖의 Service에서 처리한다. 그래야 실패한 트랜잭션이
완전히 롤백된 뒤 기존 그룹을 안전하게 다시 조회할 수 있다. 재조회 결과가 없으면 해당
예외는 `post_id` 경쟁이 아닌 FK 또는 다른 무결성 오류일 수 있으므로 그대로 전파한다.

## 오류 처리

- `postId`, `groupName`, `leaderUserId`가 없으면 `IllegalArgumentException`을 던진다.
- `approvedUserIds`가 null이거나 null 원소를 포함하면 `IllegalArgumentException`을 던진다.
- 승인 회원 목록이 비어 있는 것은 허용하며 리더만 등록한다.
- 승인 회원 중복과 모집장 중복은 오류가 아니라 정규화 대상으로 처리한다.
- 외부 모집글·사용자 존재 여부는 이번 유스케이스에서 직접 조회하지 않는다.
- 유니크 경쟁이 아닌 데이터 무결성 오류는 호출자에게 전파한다.

공통 `ErrorCode`와 전역 예외 응답 형식은 아직 확정되지 않았으므로 Part3 전용 HTTP 예외로
변환하지 않는다.

## 테스트 전략

### 명령 객체 테스트

- 정상 입력을 보존하고 승인 회원 목록을 방어적으로 복사한다.
- 필수 식별자, 그룹명, 승인 회원 목록과 null 회원 ID를 거부한다.
- 빈 승인 회원 목록을 허용한다.

### 서비스 단위 테스트

- 기존 `postId` 요청은 Writer를 호출하지 않고 기존 그룹 ID를 반환한다.
- 신규 요청은 Writer 결과를 반환한다.
- Writer의 무결성 예외 후 기존 그룹이 발견되면 기존 ID를 반환한다.
- 재조회에도 기존 그룹이 없으면 원래 무결성 예외를 전파한다.

### 트랜잭션 통합 테스트

- 신규 그룹과 초기 그룹원을 함께 생성한다.
- 모집장은 `LEADER`, 승인 회원은 `MEMBER`가 된다.
- 승인 회원 중복과 모집장 중복을 제거한다.
- 빈 승인 회원 목록이면 리더만 생성한다.
- 순차 재요청은 그룹과 그룹원을 추가하지 않고 같은 그룹 ID를 반환한다.
- 그룹원 저장 실패 시 그룹 생성까지 롤백한다.
- 병렬 요청은 그룹 하나와 정규화된 그룹원 집합 하나만 남기고 같은 그룹 ID를 반환한다.

## 문서화

이번 계약은 HTTP API가 아니라 파트 간 내부 서비스 계약이다. 구현과 함께
`docs/part3-group/api.md`에 내부 연동 계약임을 명시하고, `context.md`에는 완료 상태와 다음
작업을 갱신한다.
