# Part3 문서 정리 설계

## 목표

`docs/part3-group`의 중복·완료 작업 기록을 줄이되, 현재 구현에 필요한 계약과 결정은 보존한다. 일반 문서는 300줄 이하를 원칙으로 하고 API처럼 정보량 자체가 큰 기준 문서만 예외를 허용한다.

## 문서 역할

| 문서 | 역할 |
| --- | --- |
| `development-guide.md` | Part3 전용 개발 경계와 작업 규칙 |
| `api.md` | 현재 HTTP·내부 서비스 계약의 단일 기준 |
| `erd.md` | 테이블·관계·제약·삭제 정책의 단일 기준 |
| `context.md` | 현재 상태, 남은 작업, 다음 세션 진입점 |
| `*-design.md` | API·ERD에 없는 기능별 설계 결정 |
| `*-implementation-plan.md`, `*-plan.md` | 미완료 작업에만 필요한 실행 계획 |

## 정리 원칙

1. 완료된 구현 계획은 고유 정보를 기준 문서나 설계 문서로 옮긴 뒤 삭제한다.
2. API 요청·응답·오류는 `api.md`, 데이터 제약은 `erd.md`에서만 상세히 설명한다.
3. `development-guide.md`는 README와 공통 아키텍처 규칙을 링크로 참조하고 Part3 적용 사항만 남긴다.
4. `context.md`는 과거 작업 일지 대신 현재 HEAD 기준 완료 상태와 바로 다음 작업만 유지한다.
5. 설계 문서는 선택 이유, 불변식, 경계, 중요한 검증만 남기고 구현 절차와 반복 예시를 제거한다.
6. 실행 가능한 `schedule-fk-verification.sql`은 유지한다.

## 파일별 처리

- 완료된 대형 구현 계획은 원칙적으로 삭제한다.
- `group-home-implementation-plan.md`의 고유 계약은 `api.md` 또는 간단한 설계 문서에 흡수한다.
- 기준 문서와 설계 문서는 현재 코드·테스트와 대조해 오래된 표현을 함께 수정한다.
- 삭제되는 문서를 가리키는 링크와 문구를 모두 제거한다.

## 완료 조건

- 일반 Markdown 문서는 모두 300줄 이하이거나 초과 이유가 명확하다.
- API, ERD, 권한, 시간, 삭제 정책의 의미가 기존 계약과 달라지지 않는다.
- 완료된 상세 실행 계획과 중복된 코드·명령 예시가 남지 않는다.
- 내부 Markdown 링크가 모두 유효하다.
- `git diff --check`가 통과하고 변경 목록과 줄 수를 검토한다.
